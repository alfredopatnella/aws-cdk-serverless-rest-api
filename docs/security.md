# Security

🌐 Language: **English** | [Español](es/security.md)

This document explains the security posture of the reference architecture:
what is implemented, what is intentionally left out for educational
clarity, and what a production deployment would add.

## Security model

The threat model for this example is narrow on purpose. The goals are:

* Every Lambda function can perform only the single DynamoDB action it
  needs — nothing more.
* All input from clients is treated as untrusted and validated before use.
* Internal failures (SDK errors, exceptions, stack traces) never reach the
  client; only a small, predictable set of error shapes does.
* Traffic to the API is encrypted in transit (HTTPS, enforced by API
  Gateway).

Authentication and authorization for *callers* of the API are explicitly
out of scope — see [Authentication](#authentication) below.

## IAM least privilege

Each Lambda function has its own IAM execution role, generated by CDK, and
its own `PolicyStatement` granting exactly one DynamoDB action scoped to
the one table in this stack:

| Lambda        | DynamoDB permission | Resource            |
| ------------- | -------------------- | -------------------- |
| `create-item` | `PutItem`             | `ItemsTable` ARN only |
| `list-items`  | `Scan`                | `ItemsTable` ARN only |
| `get-item`    | `GetItem`             | `ItemsTable` ARN only |
| `delete-item` | `DeleteItem`          | `ItemsTable` ARN only |

None of these roles can call `dynamodb:*`, and none can read or write any
table other than the one this stack creates. `test/stack.test.ts` asserts
this directly: it fails the build if any IAM policy statement in the
synthesized template grants `dynamodb:*`.

Broad permissions (`table.grantReadWriteData()`, `dynamodb:*`, or a single
shared role for all four functions) would work functionally, but they
would mean a bug or vulnerability in `list-items` could, in principle, be
used to delete data — even though `list-items` never needs to delete
anything. Scoping each role to exactly what its function does removes
that failure mode entirely.

## Input validation

Client input is never trusted. Two layers validate the `POST /items`
request body:

1. **API Gateway request validation.** A JSON Schema model requires the
   body to be valid JSON containing a non-empty `title` string. Requests
   that fail this check are rejected before a Lambda is even invoked.
2. **Lambda-side validation** (`src/shared/validation.ts`). The Lambda
   independently re-validates that the body exists, parses as JSON, and
   contains a `title` string within a bounded length. This layer exists
   because the Lambda cannot assume every invocation came through this
   specific API Gateway configuration with validation enabled — direct
   test invocations, a future second API in front of the same function,
   or a misconfiguration could all bypass API Gateway's check. Validating
   again in application code is what actually enforces the rule.

Defense in depth like this is a common, deliberate pattern: each layer
protects against a different set of failure modes, and neither layer
alone is a complete guarantee.

## Error handling

Handlers catch AWS SDK errors and unexpected exceptions, log the details
to CloudWatch, and return a generic
`{ "error": { "code": "INTERNAL_ERROR", "message": "An unexpected error occurred" } }`
response. The raw exception message, stack trace, and any AWS-specific
error metadata stay in CloudWatch and are never included in the HTTP
response body.

This matters because AWS SDK error messages can reveal internal details
(table names, IAM role names, account-specific identifiers) that are
useful to an attacker and irrelevant to a legitimate client trying to fix
a bad request.

## Logging

Handlers log structured JSON lines containing the operation name, the API
Gateway `requestId`, and (for errors) the exception message — enough to
trace a specific failed request through CloudWatch. Handlers deliberately
avoid logging full request bodies or any field that isn't needed for
troubleshooting, since request bodies are user-supplied and could later
contain data that shouldn't be persisted in logs.

## Authentication

**Authentication is intentionally omitted from this educational example.**
Every route is publicly invokable by anyone with the API URL. This keeps
the example runnable with a single `curl` command and no identity
provider setup, which matters for a repository meant to be read and
tried in one sitting.

A production deployment of this architecture would add one of:

* **Amazon Cognito** — user pools issue JWTs for end users; API Gateway
  can validate them directly via a Cognito authorizer.
* **JWT authorizers** — API Gateway can validate JWTs from any OIDC-
  compatible identity provider, not just Cognito.
* **IAM authorization** — for service-to-service calls within an AWS
  environment, API Gateway can require SigV4-signed requests validated
  against IAM policies.
* **Custom Lambda authorizers** — for bespoke authentication schemes
  (API keys, third-party tokens), a Lambda authorizer runs before the
  target function and returns an IAM policy allowing or denying the
  request.

Any of these would sit in front of the existing routes in
`lib/serverless-rest-api-stack.ts` without requiring changes to the
Lambda handlers themselves, since authorization happens at the API
Gateway layer.

## DynamoDB security

DynamoDB encrypts all data at rest by default using AWS-owned encryption
keys, with no additional configuration required. For workloads with
stricter compliance requirements, a table can instead use an AWS-managed
or customer-managed KMS key. This example relies on the default
encryption, since introducing custom key management would add complexity
without a corresponding teaching benefit at this scale.

## API security improvements for production

Beyond authentication, a production-grade deployment of this same shape
would typically add:

* **AWS WAF** in front of API Gateway, to filter common web exploits and
  malicious request patterns.
* **Throttling and usage plans**, to cap request rates per client and
  protect the backend from being overwhelmed.
* **Resource policies**, to restrict which AWS accounts, VPCs, or IP
  ranges can invoke the API.
* **Private APIs** (API Gateway with a VPC endpoint), when the API should
  never be reachable from the public internet at all.
* **AWS CloudTrail**, to record management-plane API calls (who changed
  the infrastructure, and when) for audit purposes.
* **CloudWatch alarms**, to page a human when error rates, throttling, or
  latency cross a threshold.
* **Secrets management** (AWS Secrets Manager or SSM Parameter Store), for
  any credential or API key the application needs — this example has
  none, since it only talks to DynamoDB using its IAM execution role.

None of these are implemented here, because each one adds operational
surface area that isn't necessary to understand how API Gateway, Lambda,
and DynamoDB fit together — which is the point of this repository.
