Ciclo de vida de la solicitud

Cómo fluye POST /items a través del sistema

Toda solicitud sigue la misma forma de seis etapas, ya sea que esté creando, leyendo, listando o eliminando una tarea.

1

El cliente envía una solicitud JSON por HTTPS.

2

API Gateway enruta la solicitud a la Lambda correspondiente.

3

Lambda valida la entrada antes de tocar cualquier dato.

4

Lambda llama a DynamoDB con un único comando del SDK, bien acotado.

5

Lambda construye una respuesta JSON estructurada.

6

API Gateway devuelve la respuesta HTTP al cliente.

API

Cuatro endpoints, cuatro funciones Lambda

Cada ruta está respaldada por su propio handler pequeño, así que la tabla de rutas de abajo y los permisos IAM más abajo coinciden uno a uno.

POST /items

Crea una tarea a partir de un title, generando sus campos id, createdAt y completed.

GET /items

Devuelve todas las tareas mediante un Scan de DynamoDB — simple y correcto a esta escala.

GET /items/{id}

Devuelve una tarea por partition key, o un 404 estructurado si no existe.

DELETE /items/{id}

Elimina una tarea, distinguiendo un item existente (204) de uno inexistente (404).

Servicios de AWS

Qué hace cada servicio aquí

Ningún servicio de este stack se agregó por costumbre — cada uno responde a una pregunta específica sobre el sistema.

API Gateway

¿Qué es?
Una puerta de entrada HTTPS administrada que enruta solicitudes hacia integraciones backend.
¿Por qué está aquí?
Es el único punto de entrada público — TLS, enrutamiento y validación de solicitudes sin operar un servidor web.

Lambda

¿Qué es?
Un servicio de cómputo administrado que ejecuta código bajo demanda, sin servidor que aprovisionar.
¿Por qué está aquí?
Ejecuta los cuatro pequeños handlers que implementan la lógica de aplicación de la API.

DynamoDB

¿Qué es?
Una base de datos administrada de clave-valor/documentos que escala automáticamente.
¿Por qué está aquí?
Almacena de forma duradera cada item de tarea, con una simple partition key de tipo string.

IAM

¿Qué es?
El sistema de permisos de AWS — quién (o qué) puede llamar a qué acción, sobre qué recurso.
¿Por qué está aquí?
Le da a cada función Lambda exactamente una acción de DynamoDB, y nada más.

CloudWatch

¿Qué es?
El servicio de logging y monitoreo de AWS.
¿Por qué está aquí?
Cada invocación de Lambda y cada solicitud a API Gateway escriben logs aquí, que es donde se diagnostican los fallos.

CDK / CloudFormation

¿Qué es?
Infraestructura como código: TypeScript que compila a una plantilla de CloudFormation.
¿Por qué está aquí?
Define cada recurso anterior en un solo lugar, y los despliega o destruye de forma repetible.

Modelo de seguridad

Mínimo privilegio, función por función

La política IAM de cada Lambda otorga exactamente una acción de DynamoDB, limitada a la única tabla de este stack — nunca dynamodb:*.

create-item
↓
Solo PutItem

↓
Solo Scan
get-item
↓
Solo GetItem

La autenticación se omite intencionalmente en este demo para poder ejecutarlo con un único comando curl. Ver docs/es/security.md para opciones de producción (Cognito, autorizadores JWT, autorización IAM, autorizadores Lambda personalizados).

Manejo de fallos

Qué ocurre cuando una solicitud falla

Toda ruta de fallo termina de la misma forma: una pequeña forma de error JSON predecible para el cliente, y el detalle completo en CloudWatch.

Despliegue

Despliégalo, pruébalo, elimínalo

Desplegar

npm install
npm test
npx cdk synth
npx cdk deploy

Eliminar

npx cdk destroy

Elimina todos los recursos, incluida la tabla de DynamoDB — este proyecto usa RemovalPolicy.DESTROY para que un despliegue de demostración nunca quede pendiente.
