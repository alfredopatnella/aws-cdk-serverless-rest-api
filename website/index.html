Request Lifecycle

How POST /items flows through the system

Every request follows the same six-stage shape, whether it's creating, reading, listing, or deleting a task.

1

Client sends a JSON request over HTTPS.

2

API Gateway routes the request to the matching Lambda.

3

Lambda validates the input before touching any data.

4

Lambda calls DynamoDB with a single, scoped SDK command.

5

Lambda builds a structured JSON response.

6

API Gateway returns the HTTP response to the client.

API

Four endpoints, four Lambda functions

Each route is backed by its own small handler, so the routing table below and the IAM permissions further down line up one to one.

POST /items

Creates a task from a title, generating its id, createdAt, and completed fields.

GET /items

Returns every task via a DynamoDB Scan — simple and correct at this scale.

GET /items/{id}

Returns one task by partition key, or a structured 404 if it doesn't exist.

DELETE /items/{id}

Removes a task, distinguishing an existing item (204) from a missing one (404).

AWS Services

What each service is doing here

No service in this stack was added out of habit — each one answers a specific question about the system.

API Gateway

What is it?
A managed HTTPS front door that routes requests to backend integrations.
Why is it here?
It's the one public entry point — TLS, routing, and request validation without running a web server.

Lambda

What is it?
A managed compute service that runs code on demand, with no server to provision.
Why is it here?
It runs the four small handlers that implement the API's application logic.

DynamoDB

What is it?
A managed key-value/document database that scales automatically.
Why is it here?
It durably stores every task item, keyed by a simple string partition key.

IAM

What is it?
AWS's permission system — who (or what) can call which action, on which resource.
Why is it here?
It gives each Lambda function exactly one DynamoDB action, and nothing more.

CloudWatch

What is it?
AWS's logging and monitoring service.
Why is it here?
Every Lambda invocation and API Gateway request writes logs here, which is where failures get diagnosed.

CDK / CloudFormation

What is it?
Infrastructure-as-code: TypeScript that compiles to a CloudFormation template.
Why is it here?
It defines every resource above in one place, and deploys or destroys them repeatably.

Security Model

Least privilege, function by function

Every Lambda's IAM policy grants exactly one DynamoDB action, scoped to the one table in this stack — never dynamodb:*.

↓

Authentication is intentionally omitted from this demo so it can be run with a single curl command. See docs/security.md for production options (Cognito, JWT authorizers, IAM auth, custom Lambda authorizers).

Failure Handling

What happens when a request fails

Every failure path ends the same way: a small, predictable JSON error shape for the client, and full detail in CloudWatch.

↓
Lambda validation
↓
400 structured error
Unexpected exception
↓
Logged to CloudWatch

500 safe client response

Deployment

Deploy it, try it, tear it down

Deploy

npm install
npm test
npx cdk synth
npx cdk deploy

Destroy

npx cdk destroy

Removes every resource, including the DynamoDB table — this project uses RemovalPolicy.DESTROY so a demo deployment never lingers.
